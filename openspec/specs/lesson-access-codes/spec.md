# lesson-access-codes Specification

## Purpose

Give every lesson a short, stable 9-digit access number that identifies it to students, can be displayed and regenerated by the teacher, and cannot be enumerated without limit.

## Requirements

### Requirement: Automatic nine-digit assignment

The system SHALL assign every lesson exactly one access number consisting of 9 digits, drawn from 100000000 through 999999999, at the moment the lesson is created.

#### Scenario: New lesson receives a number

- **WHEN** a teacher uploads a PDF and the lesson record is created
- **THEN** the lesson is stored with a 9-digit access number that is available immediately, even while the lesson is still processing

#### Scenario: Existing lessons are backfilled

- **WHEN** the change is deployed against a database that already contains lessons
- **THEN** every existing lesson receives a unique 9-digit access number without changing its other data

#### Scenario: Number format

- **WHEN** any lesson's access number is read
- **THEN** it contains exactly 9 characters, all decimal digits, and does not begin with zero

### Requirement: Access number uniqueness

The system SHALL ensure that no two lessons share an access number, and SHALL retry assignment rather than fail lesson creation when a generated number is already taken.

#### Scenario: Collision during assignment

- **WHEN** a newly generated number already belongs to another lesson
- **THEN** the system generates another number and stores the lesson successfully once it finds an unused one

#### Scenario: Concurrent creation

- **WHEN** two lessons are created at the same time and receive the same candidate number
- **THEN** only one keeps that number and the other is assigned a different unused number

### Requirement: Number resolves to its lesson

The system SHALL resolve a valid access number to exactly the lesson that owns it and SHALL treat an unused number as not found without revealing any lesson data.

#### Scenario: Valid number

- **WHEN** a student submits a number assigned to a lesson
- **THEN** the system identifies that lesson and continues the normal student entry flow for it

#### Scenario: Unused number

- **WHEN** a student submits a 9-digit number that no lesson owns
- **THEN** the system reports that the number was not found and exposes no lesson content

#### Scenario: Number is not a share token

- **WHEN** a student opens a numeric student URL for a number that no lesson owns
- **THEN** the system shows the invalid-number message instead of a share-link error or lesson content

### Requirement: Stable access number

The system SHALL keep a lesson's access number unchanged across lesson reads, title edits, processing retries, and share-link changes, and SHALL delete it when the lesson is deleted.

#### Scenario: Unrelated updates preserve the number

- **WHEN** the teacher renames a lesson, retries processing, or creates a share link
- **THEN** the lesson keeps the same access number

#### Scenario: Deleted lesson releases its number

- **WHEN** a lesson is deleted
- **THEN** its access number no longer resolves, and a later lesson may be assigned that number

### Requirement: Teacher-visible number and regeneration

The system SHALL show the lesson's access number to an authenticated teacher on the lesson admin page and SHALL provide a round refresh control that replaces it with a new unique 9-digit number.

#### Scenario: Viewing the number

- **WHEN** the teacher opens the admin page of an existing lesson
- **THEN** the 9-digit number is displayed with a round refresh button next to it

#### Scenario: Regenerating the number

- **WHEN** the teacher activates the refresh button and confirms
- **THEN** the lesson receives a different unused 9-digit number and the admin page shows the new number

#### Scenario: Old number stops working

- **WHEN** a lesson's number is regenerated
- **THEN** the previous number no longer resolves to that lesson and the new number does

#### Scenario: Regeneration is scoped to one lesson

- **WHEN** the teacher regenerates one lesson's number
- **THEN** every other lesson keeps its existing number

#### Scenario: Unauthenticated regeneration

- **WHEN** an unauthenticated or non-teacher client attempts to regenerate a number
- **THEN** the system denies the request and the lesson keeps its current number

### Requirement: Failed-lookup throttling

The system SHALL count unsuccessful access-number lookups per client and, after 5 failures, SHALL reject further lookups from that client for 30 seconds.

#### Scenario: Fifth failure triggers lockout

- **WHEN** a client submits 5 unsuccessful access-number lookups in a row
- **THEN** the system rejects the fifth failure's follow-up attempts and reports that the client must wait 30 seconds

#### Scenario: Lockout blocks further guessing

- **WHEN** a client is locked out and submits another number, even a valid one
- **THEN** the system rejects the lookup without resolving or revealing the lesson

#### Scenario: Lockout expires

- **WHEN** 30 seconds have passed since the lockout began
- **THEN** the client may look up numbers again

#### Scenario: Successful lookup clears failures

- **WHEN** a client resolves a valid number before reaching 5 failures
- **THEN** the consecutive failure count is cleared
