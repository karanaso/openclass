# Design

## Context

See `proposal.md` - Why. `scripts/opsx-cost.mjs` currently exposes `record <stage> <ticket.md>` and `show <ticket.md>`, reading the active OpenCode session (and descendant subagent sessions) for cost and token totals. It stores a machine-readable ledger in an HTML comment inside the ticket's `## Cost` section and renders a human table beside it. `record` is already called from the propose, apply, and archive workflow copies under `.opencode/`.

Two constraints shape the approach:

- Historical calibration data is almost nonexistent. Only one ticket currently has a cost ledger, and it only has an archive-stage snapshot, so the first estimates must come from a documented fallback rather than history.
- The `.opencode` command and skill files are generated by OpenSpec 1.16.0 and have already been locally extended for cost recording. Changes must stay additive so a future `openspec update` diff is easy to reapply.

## Goals / Non-Goals

**Goals:**

- Produce a defensible estimated implementation cost for a proposal from its task list.
- Keep the estimate clearly separate from recorded actual costs and label its basis and confidence.
- Make estimation automatic in `/opsx-propose` and visible in its summary, without ever blocking the workflow.

**Non-Goals:**

- Predicting propose or archive cost separately; those stages are either already recorded or negligible.
- Building a pricing table or querying model catalogs.
- Enforcing budgets or refusing to apply when an estimate is exceeded.
- Producing exact per-task forecasts; the estimate is directional.

## Decisions

### Estimate from the change's task count

Add `estimate <ticket.md> --change <change-dir>` to `scripts/opsx-cost.mjs`. The command reads `<change-dir>/tasks.md`, counts tracked checkboxes matching `^\s*-\s*\[[ xX]\]`, and accepts `--tasks <n>` as an override for non-standard task files. Counting in the script keeps the number consistent with what the apply workflow will actually track.

- Alternative considered: have the agent count tasks and pass a number. Rejected because agents can miscount nested lists and the script already knows the file layout.

### Median cost per completed task, with a documented fallback

Calibrate `perTaskCost` from existing tickets that have both an `apply` stage entry in their ledger and a `Tasks: X/Y` line with `X > 0`: compute `applyCost / X` for each and take the median. Use the calibrated value only when at least 3 such samples exist; otherwise use a default baseline constant.

Estimated implementation cost is `max(floor, tasks * perTaskCost)`, with a range of roughly half to one-and-a-half times the point estimate. Start with `perTaskCost = $0.05` and `floor = $0.10` as constants in the script, chosen to land near the observed size of recent small changes and easy to tune in one place.

- Why a median: a single large or shared session would otherwise skew the baseline. Why a minimum sample size: one or two tickets are not a calibration.
- Alternative considered: token-based estimation from file counts. Rejected because it adds a second heuristic without better data; task count is the unit the change already tracks.
- Alternative considered: LLM-produced dollar estimates. Rejected for reproducibility; the agent should report a number the script can defend.

### Store the estimate in the same `## Cost` section

Extend the ledger comment with an optional `estimate` object (`{ amount, low, high, tasks, perTaskCost, basis, samples, at }`) while keeping the existing `stages` array. Render the estimate above the actual table:

```
Estimate: **$0.35** (range $0.18–$0.53) for 7 tasks.
Basis: default baseline ($0.05/task); 0 historical apply samples.
```

`record` preserves the estimate; `estimate` preserves recorded stages. Re-proposing refreshes the estimate. This keeps one cost section per ticket instead of a second source of truth.

- Alternative considered: a separate `## Estimate` section. Rejected because users already look at `## Cost`, and splitting the two makes estimate-vs-actual comparison awkward.

### Report estimate vs actual during apply

When `/opsx-apply` records its cost, print the estimate and the actual apply-stage cost with the delta. No new tracking data is needed: the apply ledger row already captures the actual amount.

### Test the CLI as a user would run it

Add `tests/opsx-cost-estimate.test.ts` that creates temporary ticket and change directories, writes fixture `tasks.md` files, and invokes the script with `execFileSync`. Assert the printed summary and the ticket's `## Cost` content for: fallback baseline, calibrated median with 3+ samples, task-count override, and estimate preservation across a subsequent `record`.

- Alternative considered: exporting internal functions for unit tests. Rejected because the script runs `main()` at import time; CLI-level tests cover argument parsing and file rendering without a refactor that is not needed yet.

## Risks / Trade-offs

- **Estimates are wrong early** → Label the basis and sample count, show a range, and describe the number as an estimate. Calibration takes over automatically once 3 apply-stage samples exist.
- **Task count ignores complexity** → Keep the wide range and let the user treat the point estimate as directional; complexity outliers still appear in the proposal review.
- **Shared sessions inflate actual apply cost** → The existing caveat about counting a shared session in full already applies to actuals; estimates inherit the same upper-bound bias.
- **Generated `.opencode` files drift from upstream** → Keep edits additive and near the existing cost steps; document the dependency in the proposal so a future template update is a small merge.
- **`record` and `estimate` clobber each other** → Both must preserve the other half of the ledger; the tests cover this explicitly.

## Migration Plan

No data migration. Existing tickets without a ledger simply gain an estimate on the next propose; tickets with recorded stages keep them. Roll back by reverting the commit; the extra `estimate` ledger field is ignored by older readers.
